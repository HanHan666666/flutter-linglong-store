# 架构治理路线与应用操作 Journal 优化设计

## 1. 文档定位

本文记录 2026-07-30 架构审计后确认的治理顺序、各阶段边界，以及第一阶段
“应用操作 Journal 高频写入与持久化屏障”的详细设计。

本轮治理不是为了追求抽象层数，而是降低后续功能修改的影响面，并优先消除会
直接影响 UI 响应、恢复正确性和长期维护成本的问题。每个阶段必须可以独立验证、
独立提交和独立回滚，不把多个目标混在一次大规模重写中。

## 2. 审计结论

### 2.1 P0：Journal 写放大

`InstallQueue` 当前会在每条 `ll-cli --json` 进度消息到达时：

1. 把新的命令输出追加到 `InstallTask.commandOutput`；
2. 复制完整 `InstallQueueState`；
3. 在 UI isolate 同步执行完整快照的 `jsonEncode`；
4. 把一次原子文件写入追加到无界的 Future 串行链。

任务日志会随执行时间持续增长，Journal 又同时包含等待队列、当前任务、历史、
批次和 Outbox，因此每条消息都会重复编码和写入不断变大的快照。长时间更新或
高频进度输出会形成明显的主 isolate 计算放大和磁盘写入积压。

此外，`AppOperationLifecycleCoordinator` 直接监听内存中的 Outbox。终态虽然
已经排队保存，但副作用可能在对应快照真正落盘前开始执行。若此时进程退出，
外部副作用和可恢复事实可能不一致。

### 2.2 P1：安装队列职责过多

`install_queue_provider.dart` 同时负责：

- 依赖装配和旧数据迁移；
- 队列命令与状态转换；
- `ll-cli` 流消费；
- 取消、超时和恢复；
- 批次与 Outbox；
- Journal 映射；
- 面向用户的错误文案。

任何修改都需要理解整套状态机，文件冲突概率和回归半径都过大。

### 2.3 P1：分层依赖和错误边界不清晰

Application 层存在直接依赖 Data、Platform 实现和 `core/di/providers.dart`
聚合出口的情况。部分 Data 实现还会生成本地化字符串，Domain Repository
也使用 `String` 或空列表同时表达业务结果和失败。这让上层无法稳定区分
“确实没有数据”“命令失败”和“解析失败”，切换语言后持久化文案也可能保留
旧语言。

### 2.4 P2：高风险大文件和生成物约定漂移

环境管理服务、环境管理对话框、应用详情页、下载管理弹窗和标题栏均已承担多个
独立职责。生成代码同时存在“部分提交、部分忽略”的混合策略，CI 只生成而没有
验证工作区是否一致。现有架构文档也未完整反映 Application、Data 和 Platform
的实际依赖。

## 3. 治理原则

1. **正确性优先于吞吐量**：任务终态、Outbox 和批次结果必须先持久化，后执行
   外部副作用。
2. **UI 状态与持久化职责分离**：UI 可立即看到内存进度；磁盘只需要保留最新的
   可恢复快照，不需要逐条回放进度。
3. **依赖指向稳定抽象**：业务编排只依赖 Domain 契约，具体实现集中在应用组合根。
4. **状态保存事实，不保存展示策略**：错误、状态和操作结果保存结构化信息，
   Presentation 在当前 locale 下生成文案。
5. **按可独立提交的边界拆分**：先建立新边界并迁移调用方，确认稳定后再删除旧边界。
6. **不过度设计**：只有已有两个以上调用场景或明确的变化轴时才提取通用抽象。
7. **测试服务于风险**：只补持久化、恢复、并发合并、状态迁移和依赖约束等真实
   风险测试，不为覆盖率制造无业务价值的测试。

## 4. 分阶段路线

### 阶段一：Journal 合并写与持久化屏障

目标：

- 把无界写入链收敛为“最多一个正在写、一个等待写”的 latest-wins 队列；
- 只有真正开始写入的快照才执行 JSON 编码；
- 为终态、Outbox 消费和任务启动提供明确的 durable barrier；
- 保持现有 Journal 文件格式和恢复兼容性不变。

独立提交建议：

- `perf: 合并应用操作 Journal 高频写入`

### 阶段二：收敛应用组合根

目标：

- 新建顶层 `bootstrap/di` 组合根；
- Application Provider 只依赖 Domain 契约或相邻 Application 能力；
- Data、Platform 的具体实现只在组合根实例化；
- 拆除 `core/di/providers.dart` 反向导出 Application Provider 的循环聚合。

独立提交建议：

- `refactor: 收敛应用依赖注入组合根`

### 阶段三：拆分安装队列状态机

按变化原因拆为：

- 队列命令与纯状态转换；
- 单任务执行和 `ll-cli` 事件适配；
- 启动恢复和实例核验；
- Journal 快照映射；
- 批次及 Outbox 推导。

Riverpod Notifier 只保留用例入口和状态发布，不再实现所有细节。拆分过程中必须
保持以下协议不变：

- 同时只运行一个任务；
- taskId 是操作唯一身份；
- 一键更新完成只由批次自身目标快照推导；
- 恢复更新任务必须核验实例和 `expectedVersion`；
- 队列、当前任务、历史、批次和 Outbox 仍在同一快照中原子保存。

独立提交建议：

- `refactor: 拆分应用操作队列职责`

### 阶段四：结构化错误与国际化边界

目标：

- Domain 定义稳定的失败类型、错误类别和诊断信息；
- Data 只解析命令结果，不生成 UI 文案；
- Application 决定重试、恢复和状态迁移；
- Presentation 使用当前 locale 把结构化状态格式化为用户文案；
- 明确区分空结果、命令执行失败和输出解析失败。

该阶段需要版本化迁移已持久化的旧 `errorMessage/displayMessage` 字段；兼容读取
旧快照，但新写入逐步只保存结构化字段。

独立提交建议：

- `refactor: 统一应用操作错误边界`
- `refactor: 收敛命令仓库结果类型`

### 阶段五：拆分环境管理和高频 God Widget

优先顺序：

1. `LinglongEnvironmentManagementService` 按健康检查、修复、权限、迁移拆分；
2. 环境管理对话框按 Section 和交互 Controller 拆分；
3. 下载管理弹窗按概览、当前任务、等待列表和历史列表拆分；
4. 应用详情页按头部、版本列表和操作编排拆分；
5. 标题栏和设置页只在职责边界明确时继续拆分。

只做结构迁移，不同时调整视觉或业务语义，避免重构与功能变化互相掩盖。

独立提交建议：

- `refactor: 拆分玲珑环境管理服务`
- `refactor: 拆分玲珑环境管理界面`
- `refactor: 拆分下载管理界面`
- `refactor: 拆分应用详情页面`

### 阶段六：统一生成文件与架构文档

先选择并固定一种仓库策略：

- **提交生成物**：CI 运行生成命令后必须验证 `git diff --exit-code`；
- **不提交生成物**：删除已跟踪生成物，构建和开发入口统一先生成。

Flutter 桌面打包更适合提交稳定生成物，避免离线打包依赖代码生成环境，因此本项目
默认采用第一种策略。最终同步更新架构图、目录职责、依赖规则和开发指南。

独立提交建议：

- `build: 统一 Flutter 生成文件校验`
- `docs: 更新 Flutter 分层架构约定`

## 5. 第一阶段详细设计

### 5.1 方案比较

#### 方案 A：固定时间防抖

例如每 100 毫秒保存一次进度。实现简单，但需要额外处理终态立即刷新、定时器释放、
应用退出和测试时钟；磁盘较慢时仍会继续形成写入队列。

#### 方案 B：每次写入都创建 isolate

可降低 UI isolate 的编码开销，但不能减少磁盘写次数和快照复制次数。小快照频繁
创建 isolate 还会增加调度与复制成本，属于在未测量前引入复杂度。

#### 方案 C：仓库内部 latest-wins 合并写

仓库始终只保留：

- 一个正在原子写入的快照；
- 一个尚未开始、可以被更新快照替换的槽位。

多个等待请求共享被选中快照的完成结果。该方案不需要时间窗口，天然适应磁盘速度，
并直接限制积压上界。

**选择方案 C。** 第一阶段不引入 isolate。合并写完成后再用真实最大 Journal
快照测量编码耗时；只有编码仍持续超过一帧预算时，才考虑常驻 worker isolate，
而不是每次 `Isolate.run`。

### 5.2 保存语义

`AppOperationJournalRepository.save(snapshot)` 的 Future 必须满足：

- Future 完成时，该快照或一个更新的快照已经成功原子落盘；
- 若快照 B 在开始写入前被 C 替换，B 和 C 的等待者都在 C 落盘后完成；
- 正在写入的 A 不会被中断；B、C 只合并等待槽；
- 某次写入失败只使该次覆盖的等待者失败，不能永久阻断后续新快照；
- JSON 编码在快照从等待槽进入实际写入时执行，不在 `save` 调用处执行。

该语义允许调用方把 Future 当作持久化屏障，同时避免为每条进度保存中间态。

### 5.3 写入状态机

```text
idle
  │ save(A)
  ▼
writing(A) ── save(B) ──► writing(A) + pending(B)
    │          save(C) ──► writing(A) + pending(C)
    │
    ├─ A 成功：完成 A 的等待者，开始写 C
    └─ A 失败：A 的等待者失败，仍尝试写 C
```

任意时刻快照槽位数量最多为 2，空间和待写次数不再随进度消息数量增长。

### 5.4 队列持久化屏障

`InstallQueue` 继续先发布内存状态以保证 UI 响应，但记录最近一次保存 Future，并
暴露 `waitForPendingPersistence()`：

1. 捕获当前保存 Future；
2. 等待其完成；
3. 若等待期间出现更新的保存 Future，则继续等待；
4. 直到观察到的 Future 仍是最新保存为止。

屏障用于以下边界：

- 生命周期协调器读取和消费 Outbox 前；
- 把等待任务提升为当前任务并启动 `ll-cli` 前；
- 当前任务进入终态并准备调度下一任务前。

这样可以保证外部副作用和不可逆命令不会领先于可恢复事实。普通进度渲染不等待磁盘，
仍保持高响应。

### 5.5 Outbox 消费顺序

协调器每轮消费前执行：

1. 等待队列最新状态持久化；
2. 重新读取队列状态，而不是继续使用等待前的对象；
3. 获取当前首条 Outbox 事件；
4. 标记尝试次数并再次等待该变更持久化；
5. 执行外部副作用；
6. 确认事件并由下一轮屏障保证确认结果落盘。

副作用执行失败仍遵循现有“尽力执行并确认”的业务规则，但不得在事件自身尚未持久化
时执行。

### 5.6 日志边界

`InstallTask.commandOutput` 当前是下载管理和详情页“复制日志”的唯一来源，本阶段
不截断、不外置，避免改变已确认的产品行为。合并写会先消除最严重的重复编码和磁盘
队列问题。

后续如真实最大快照仍影响性能，再单独设计 XDG State 下的按 taskId 日志文件：

- Journal 只保存日志引用和有限诊断摘要；
- 日志文件采用追加写；
- 任务删除时精确清理；
- 迁移期间继续兼容旧快照内嵌日志。

该工作必须作为独立功能设计和提交，不能夹带在本阶段。

### 5.7 文件格式与 XDG 兼容

本阶段不修改 `AppOperationJournalSnapshot` JSON schema，也不改变路径：

```text
$XDG_STATE_HOME/com.dongpl.linglong-store.v2/operations/queue-v2.json
```

临时文件继续与正式文件处于同一目录，并通过 rename 原子替换。不存在
`XDG_STATE_HOME` 时沿用既有 XDG 路径解析规则，不新增发行版或桌面环境判断。

### 5.8 验证范围

只增加能保护真实并发风险的测试：

- 高频 save 最终只保留最新快照；
- 等待槽被替换时，旧调用者在最新快照落盘后才完成；
- 正在写入失败不阻断等待槽中的较新快照；
- 持久化屏障会等待期间出现的更新保存；
- 现有损坏快照保留和原子读写测试继续通过。

同时执行：

- `dart format`；
- 相关 Journal、队列和生命周期测试；
- `flutter analyze`；
- Linux release 构建在阶段性重构完成后统一验证。

## 6. 完成标准

本轮治理全部完成时应满足：

- 高频进度不再产生无界 Journal 写入积压；
- 任务执行和 Outbox 副作用有明确的持久化先行保证；
- Application 不再直接实例化 Data/Platform 实现；
- 队列、恢复、执行、Journal 和批次推导拥有清晰边界；
- Data 不负责本地化展示文案，失败结果可被稳定分类；
- 高风险服务和 Widget 按变化原因拆分；
- 生成物策略由 CI 强制执行；
- 架构文档与实际依赖一致。
